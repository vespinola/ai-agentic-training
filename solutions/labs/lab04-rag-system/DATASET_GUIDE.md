# Dataset Guide For Lab 04

This guide explains how to create an evaluation dataset for a new codebase in the format used by this project.

## Why The Dataset Exists

The evaluation dataset gives the RAG system a set of known test cases.

Each example helps answer two separate questions:

1. Did retrieval find the right chunk?
2. Did generation produce the right answer?

Without a dataset, evaluation becomes subjective and hard to compare over time.

## Dataset Format

Each example in `evaluation_dataset.json` looks like this:

```json
{
  "id": "q3",
  "question": "Which function creates auth tokens?",
  "expected_answer": "Token creation happens in auth.py inside create_token.",
  "relevant_docs": ["auth.py::function::create_token::16"]
}
```

Fields:

- `id`: unique label for the test case
- `question`: the user question you want to test
- `expected_answer`: the answer the system should ideally produce
- `relevant_docs`: one or more chunk IDs that contain the answer

## How To Build A Dataset Step By Step

### 1. Index the codebase first

The dataset depends on the chunk IDs generated by the chunker, so index the files before writing the final `relevant_docs`.

That means your order is:

1. choose the codebase
2. index it
3. inspect chunk IDs
4. write the dataset

### 2. Pick clear, answerable questions

Good questions are:

- specific
- grounded in one or a few chunks
- realistic for users
- easy to verify

Examples:

- `Which function hashes passwords?`
- `Where is JWT validation implemented?`
- `Which handler returns invalid credentials?`
- `How is the health response defined?`

Weak questions:

- `How does this app work?`
- `Is this code good?`
- `What should be improved?`

Those are too broad for clean retrieval evaluation.

### 3. Write the expected answer

The expected answer should be:

- short
- factual
- directly supported by the code

Good expected answer:

- `Password hashing is implemented in auth.py by the hash_password function.`

Weak expected answer:

- `The application handles password operations in a secure and maintainable way.`

That is too vague and harder to judge.

### 4. Find the correct chunk ID

This is the most important part for retrieval evaluation.

The backend creates IDs in this format:

```text
file_path::chunk_type::symbol_name::line_start
```

Example:

```text
auth.py::function::create_token::16
```

That means:

- file: `auth.py`
- chunk type: `function`
- symbol: `create_token`
- starts on line `16`

Your `relevant_docs` field should contain the chunk ID or IDs that actually answer the question.

### 5. Repeat until you have enough coverage

The lab asks for `10+` examples, but do not make them all the same kind.

Try to include variety such as:

- auth logic
- config
- request handlers
- data lookup
- response formatting
- error handling
- utility functions

This makes the evaluation more representative.

## What Makes A Strong Example

A strong example usually has:

- one clear question
- one narrow answer
- one obvious supporting chunk or a small set of chunks
- language that matches how a real user might ask the question

Example:

```json
{
  "id": "q8",
  "question": "Where are required registration fields checked?",
  "expected_answer": "Registration field validation is done in app.py by register_handler.",
  "relevant_docs": ["app.py::function::register_handler::4"]
}
```

Why this is strong:

- it asks about one clear behavior
- the answer lives in one function
- the retrieval target is easy to define

## When To Use Multiple Relevant Docs

Sometimes one question needs more than one chunk.

Example:

- `How does login work from credential lookup to token creation?`

That might involve:

- a lookup function
- a password verification function
- a token creation function

Then `relevant_docs` can contain multiple IDs:

```json
{
  "id": "q11",
  "question": "How does login work from credential lookup to token creation?",
  "expected_answer": "Login first finds the user, validates the password, and then creates a token.",
  "relevant_docs": [
    "users.py::function::login::19",
    "users.py::function::find_user_by_email::12",
    "auth.py::function::create_token::16"
  ]
}
```

This is useful for recall testing.

## How To Inspect Chunk IDs

The easiest way is to index the files and inspect the stored chunks or query results.

In this project, chunk IDs appear in:

- query results
- evaluation results
- the local `rag_index.json` file after indexing

If you want a fast manual workflow:

1. load or index the codebase
2. ask a very direct question
3. inspect the returned source IDs
4. use those IDs in your dataset if they really are the correct chunks

## Common Mistakes

- writing questions that are too broad
- writing expected answers that are too vague
- using chunk IDs from an old version of the code
- forgetting that chunk IDs can change if line numbers change
- reusing the sample dataset for a different codebase
- choosing questions with no single ground-truth chunk

## Important Limitation

Chunk IDs depend on the current file contents and chunking logic.

That means if:

- the code changes
- the chunker changes
- line numbers shift

then some `relevant_docs` IDs may need to be updated.

This is normal. Evaluation datasets often need maintenance as the indexed content evolves.

## Recommended Workflow For Students

For a new codebase, use this process:

1. index the codebase
2. choose 10 to 15 realistic questions
3. write short expected answers
4. identify the correct chunk IDs
5. save the dataset
6. run `/evaluate`
7. inspect bad retrieval or weak answers
8. improve chunking, ranking, or prompting
9. evaluate again

That loop is exactly the habit Lab 04 is trying to teach.
